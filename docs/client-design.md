# 클라이언트 설계 — daily-special-client

> 클라가 무엇을 맡고 무엇을 안 맡는가, 그리고 어떤 순서로 만드는가.
> 이 문서는 자체 완결로 쓴다. 외부 문서를 참조하지 않는다.
> 최종 수정: 2026-08-06

---

## 0. 순서 — 게임 로직보다 빌드 확인이 먼저다

```
1단계  목 JSON 읽기 → 한글 표시 → APK 폰 설치      ← go/no-go
2단계  하루 사이클 척추 — 장보기 · 손님 1명 · 요리 · 반응
3단계  만족도 엔진 이식 + 손님 여러 명
4단계  관계 = 정보 (취향 공개 곡선)
5단계  아트 통합 · 폴리시
```

**1단계를 먼저 하는 이유가 이 문서에서 가장 중요하다.**

빌드 확인이 뒤로 밀리면 폰트·빌드 문제를 며칠 쓴 뒤에 발견한다. 그런데 1단계는 **버려지는 작업이 아니다** — 목 JSON을 읽어 한글을 띄우는 화면이 그대로 척추의 시작이다. 그래서 별도 "스파이크" 단계를 두지 않고 순서로만 지킨다.

**판정**: 폰에서 한글 이름·소개가 보이면 go. 빌드가 안 되거나 폰트가 깨지면 웹(Phaser/React + Capacitor)으로 전환한다. **"에디터에선 되는데 폰에선 안 된다"도 no-go로 취급한다** — 제출물이 빌드다.

## 1. 클라가 맡는 것

| | 무엇 |
|---|---|
| **화면 전부** | 하루 사이클 UI, 장보기, 조리 슬라이더, 손님 대사, 정산 |
| **만족도 엔진** | 파이썬 레퍼런스를 C#으로 이식 (2절) |
| **콘텐츠 로딩** | `Assets/Resources/*.json` 파싱 |
| **대사 선택** | (상황 × 대상 × 말투)로 풀에서 고르기 |

## 2. ⭐ 만족도 엔진 이식

**이 게임의 AI 차별점이 여기 있다.** 손님의 판단에 런타임 LLM을 부르지 않는다 — 오프라인에서 LLM이 만든 페르소나를 결정적 함수가 평가한다.

```
만족 = 욕구 충족도 × 취향 일치도 × 예산 적합 × 식이 계수     (전부 곱셈, 결과 0~1)
```

곱셈인 이유: 하나라도 0에 가까우면 전체가 낮아진다. 덧셈이면 한쪽만 잘해도 통과해버린다.

**레퍼런스와 명세**

- 구현: `daily-special-pipeline`의 `src/daily_special/domain/satisfaction.py`
- **명세: 같은 저장소의 `tests/test_satisfaction.py` 23건**

이식할 때 그 테스트 케이스를 C#으로 옮겨 전부 통과시킨다. 통과하면 두 구현이 어긋나지 않는다.

**여기 요약본을 만들어두지 않는다.** 이식 시점에 원본을 직접 보고 옮긴다 — 두 벌이 되면 요약본이 뒤처지고, 그때 어느 쪽이 맞는지 알 수 없다.

**도메인은 `UnityEngine`을 모른다** (`conventions.md` 1절). `MonoBehaviour`에 넣으면 EditMode 테스트로 23건을 돌릴 수 없고, 그러면 이식이 맞는지 확인할 방법이 사라진다.

## 3. 클라가 **안** 맡는 것

플레이 중에 바뀌는 것은 **서버가 소유한다** (계약 5절). 서버 API가 아직 없다고 클라가 만들면 나중에 두 번 만든다.

| 서버 소유 | 클라는 지금 |
|---|---|
| 손님의 오늘 상태 (허기·컨디션·기분·**지갑**) | 로컬에서 임시로 만든다. **한 곳에 모아둔다** |
| 오늘의 욕구 뽑기 | 같음 |
| 관계 수치·단골 여부·공개된 취향 | 같음 |
| 평판·소지금·재고 | 같음 |
| 시장의 그날 시세 | 같음 |

**임시 구현을 한 곳에 모아두는 것이 중요하다.** 서버 API가 붙으면 그 자리만 네트워크 호출로 바꾼다. 화면 여기저기에 흩어 놓으면 서버 붙일 때 전부 찾아다녀야 한다.

## 4. 데이터

`Assets/Resources/`에 파이프라인 생성분 4종이 있다. 클라 번들에 넣어 오프라인에서도 읽는다.

| 파일 | 무엇 | 개수 |
|---|---|---|
| `guests.json` | 손님 페르소나 — 정체성·말투·취향 구간·선호 욕구·식이 제약 | 8 |
| `ingredients.json` | 재료 — 신선/보존·기준가·식이 저촉 | 12 |
| `dishes.json` | 요리 — 욕구 태그·필요 재료·고정가 | 10 |
| `lines.json` | 대사 — 전 상황 × 대상 × 말투 | 80 |

필드 구성은 `data-contract.md` 7~10절에 있다.

**유도되는 값 셋**은 파일에 없다. 계산해서 쓴다 (계약 9-1절).

- 요리의 **식이 저촉** = 쓴 재료들의 저촉 합집합
- **상시/오늘의 메뉴** 구분 = 신선 재료가 하나라도 있으면 오늘의 메뉴
- **파라미터 3축**은 요리의 속성이 아니다 — 플레이어가 매번 맞추는 값이다

`lines.json`은 인사·주문·고/저 만족 반응·축별 피드백·퇴장 상황을 포함한다. 대사 선택은
상황 × 대상 × 말투로 이 파일에서 한다.
